MANAK SETU — COMPLETE PROJECT IMPLEMENTATION PLAN

Version: 1.0 Purpose: Controlled full-stack implementation plan for the
existing BIS AI Assistant project

IMPORTANT: This document is an implementation specification, not
permission to blindly rewrite the existing project. The existing
backend, database, authentication, RAG pipeline, storage, and working
frontend behavior must be inspected before modification. If the actual
repository differs from any assumption in this document, STOP, document
the discrepancy, and adapt only after verification.

======================================================== 0. MASTER
OBJECTIVE ========================================================

Build and complete “Manak Setu”, a BIS-focused AI-powered compliance and
information web application that:

1.  Helps users identify applicable Indian Standards from
    natural-language product descriptions.
2.  Provides a Product Certification Guide with a structured 6-stage
    compliance roadmap.
3.  Provides BIS certification and QCO guidance.
4.  Provides testing and laboratory guidance.
5.  Provides required-document guidance and document upload/AI scanning
    capability where supported.
6.  Provides an accurate, database-driven Fee & Cost Estimator.
7.  Provides Consumer Help, including Hallmarking guidance.
8.  Provides a persistent AI Assistant available from the lower-right
    corner.
9.  Supports multilingual application text through i18n.
10. Supports dynamic AI responses in the selected language through the
    backend AI API.
11. Provides source-backed answers with specific BIS document/PDF
    references.
12. Works as a Progressive Web App (PWA) with an Install Application
    option.
13. Preserves the existing custom authentication system unless a
    deliberate migration is approved.
14. Uses existing Supabase PostgreSQL/pgvector data instead of inventing
    duplicate data.
15. Keeps the interface simple, official, trustworthy, readable,
    responsive, and non-cluttered.

The application is intended for manufacturers, MSMEs, startups,
students, consumers, and other users who need BIS-related information
without manually searching many documents and portals.

======================================================== 1.
NON-NEGOTIABLE SAFETY RULES FOR IMPLEMENTATION
========================================================

RULE 1 — INSPECT BEFORE CODING Do not begin by replacing files or
generating a new application. First inspect: - repository root - current
Git branch/status - frontend structure - backend structure -
api_server.py and all imported backend modules - API routes and
request/response models - authentication flow - database connection
code - Supabase usage - pgvector/RAG retrieval functions - Gemini
integration - chat history handling - file upload handling - storage
integration - existing frontend routes/pages/components/services -
existing environment variables - current build configuration - current
PWA configuration, if any

RULE 2 — DO NOT DELETE EXISTING BACKEND FILES Do not delete, rename, or
replace backend files merely because they look unnecessary. Do not
remove code that has not been explicitly approved for removal.

RULE 3 — DO NOT INVENT API CONTRACTS The actual backend source code is
the authority. Do not assume endpoint names, payload fields, response
fields, status codes, authentication requirements, or file-upload
formats. Record the verified contract before changing the frontend.

RULE 4 — DO NOT INVENT DATABASE DATA Do not hardcode BIS standards,
QCOs, fees, laboratory information, testing requirements, certification
requirements, or document requirements when the information is expected
to come from the database. If the database has no relevant record, show
a clear “No details available yet” state rather than fabricated
information.

RULE 5 — DO NOT “CLEAN UP” THE DATABASE AUTOMATICALLY The current schema
contains both UUID and text-based standard identifiers and both newer
and older standard/chunk structures. Do not merge, rename, convert,
migrate, or delete these structures simply for consistency. First trace
which structures are used by the existing backend.

RULE 6 — PRESERVE WORKING AUTHENTICATION The current application has
custom authentication using a users table, OTPs, password hashes,
JWT/HttpOnly-cookie behavior, and verification state. Do not migrate to
Supabase Auth unless explicitly approved.

RULE 7 — NO BACKEND LEAKAGE INTO USER UI Do not display internal
implementation details such as: - RAG server wording - cosine distance -
embedding scores - raw vector-search details - raw storage paths - raw
filenames when a human-readable document title exists - internal
prompts - internal model names - stack traces

RULE 8 — FAILURE MUST BE USER-SAFE Every external/API operation must
have: - loading state - success state - failure state - timeout behavior
where applicable - retry behavior where applicable - no broken/blank
UI - no unhandled promise rejection

RULE 9 — DO NOT DUPLICATE REQUESTS A retry must not leave the previous
request running. Prevent double-click submission and duplicate API
calls.

RULE 10 — VERIFY AFTER EACH PHASE Do not continue to the next major
phase if the previous phase fails its acceptance tests.

======================================================== 2. EXISTING
BACKEND — VERIFIED ARCHITECTURAL CONTEXT
========================================================

Backend: - Python - FastAPI - Google GenAI SDK - Supabase PostgreSQL -
pgvector - custom JWT HttpOnly cookie authentication

Knowledge/RAG concept: - BIS/product-manual content is chunked into
standard_chunks. - Chunks contain standard identifiers, page numbers,
content, and embeddings. - User questions are embedded and compared
against vector data. - Retrieved context is injected into Gemini
generation. - The backend is responsible for AI generation and document
retrieval.

Known backend areas requiring attention: 1. Naive retrieval currently
embeds the raw user query instead of rewriting context-dependent
follow-up questions. 2. Follow-up questions can lose context. 3.
Retrieval limits are currently restrictive (top_k=4 and threshold=0.5
were identified as limitations). 4. Generation is overly restrictive for
readable structured answers. 5. Frontend roadmap requires structured
data, while the current backend can return conversational text. 6.
In-memory chat_sessions can lose history on server restart.

These are implementation issues to verify against the actual current
code before changing.

======================================================== 7. MULTILINGUAL
ARCHITECTURE ========================================================

IMPORTANT: Static application text and dynamic AI-generated text are two
different translation problems.

A. STATIC UI TEXT Use i18n.

All fixed UI strings must come from translation resources: -
navigation - buttons - headings - labels - placeholders - validation
messages - loading text - error text - empty states - accessibility
labels - tooltips - modal text - common system messages

Do not create duplicated hardcoded English/Hindi strings inside
components.

B. DYNAMIC AI TEXT Do NOT pre-write translations for AI answers.

The selected language must be sent to the backend AI API. The backend
must instruct the AI to answer in the selected language while
preserving: - facts - BIS terminology - standard numbers - clause
numbers - document references - numerical values - source citations

C. FALLBACK If the AI API takes more than 10 seconds or the API server
is unavailable: - stop waiting - display a translated, user-friendly
fallback message - offer Retry - do not expose stack traces or server
errors

The fallback itself must be handled by i18n.

Recommended language architecture: Frontend: selectedLanguage = “en” |
“hi” | future supported languages

API: { message: “…”, language: “hi”, … }

Backend: - receives language - retrieves BIS context - generates answer
in requested language - returns structured response

======================================================== 8. 10-SECOND
AI/API TIMEOUT ========================================================

The 10-second requirement applies to the frontend waiting for an AI/API
response.

Required sequence: REQUEST A STARTS → user cannot accidentally send
duplicate requests → wait up to 10 seconds → if no successful response:
abort/cancel REQUEST A show fallback show Retry → Retry creates REQUEST
B → REQUEST A must not continue updating the UI

Handle: - connection refused - network error - timeout - 4xx - 5xx -
malformed response - empty response

Do not use the timeout as an excuse to fabricate an AI answer.

======================================================== 20. RAG
IMPROVEMENT PLAN
========================================================

Current issues to investigate: 1. Raw query embedding. 2. Follow-up
context loss. 3. top_k=4 restriction. 4. threshold=0.5 restriction. 5.
insufficient retrieval for multi-page compliance. 6. SIT/test-clause
retrieval gaps. 7. volatile in-memory chat_sessions.

Improvement approach:

A. Query rewriting Before vector search, rewrite context-dependent
follow-up questions into a standalone retrieval query using conversation
context.

B. Hybrid retrieval Where practical, combine semantic/vector retrieval
with keyword/metadata filtering.

C. Adaptive retrieval Do not blindly use a fixed top_k for every
question. Use an appropriate retrieval strategy based on question
complexity and available evidence.

D. Metadata filtering Use standard/product/document/page information to
improve relevance.

E. Multi-page context Allow enough relevant chunks to answer questions
spanning multiple pages, while preventing excessive irrelevant context.

F. Evidence preservation Every answer should preserve source
document/page references where available.

G. SIT-specific retrieval Testing questions should prioritize Scheme of
Inspection and Testing sections/annexures when present.

H. Persistent history Use chat_history or an appropriate durable
mechanism instead of relying solely on an in-memory dictionary.

Do not implement these changes until existing RAG functions and database
queries have been inspected.
